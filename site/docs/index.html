How Liny~Sync works

From the first run to the brief your agent finishes.

StatusWhat you needFirst runConnectPick and moveWhere things landThe briefSecurityCommand line

Status

LinySync is in early development and not released yet. It runs AnySync's engine with Linux on both ends: only Linux machines are listed and accepted, whatever their distro. Working today: device identity and looks, the bus repo, the item catalogue, offers and picks, the encrypted machine to machine stream with resume, placing and the brief, in the window and on the command line. CI tests and builds it on Linux, and a tagged version makes a release with linysync-linux-x64.tar.gz.

What you need

  • Two Linux machines running LinySync, of any distro. The window needs the usual X11 or Wayland libraries.
  • One GitHub account, signed in with the GitHub CLI (gh auth login) on both, or a token in LINYSYNC_TOKEN.
  • The two machines on the same network, so they can reach each other directly.
  • For the last step, any AI agent you like to read GOAL.md.

First run

LinySync gives the device a random eight digit id and keeps it, the name, the look and a key pair in its own folder: ~/.config/linysync. On first use it makes your private bus repo, <login>/linysync-bus, and registers the machine there with its distro and public key.

Connect

On the Connect tab, press Find devices on this account and pick the other machine. Choose to send or to receive; the other device shows the request, and its owner approves or declines. The direction holds for this transfer only.

Pick and move

The sender offers a tree of what it has, grouped by kind. Each item shows where it lands on the new machine. Tick what you want; only those travel, straight between the two devices. Folders rebuilt from source (node_modules, target, .venv, __pycache__ and the like) stay behind. If the connection drops, the receiver asks again for what has not arrived, up to 20 times.

Where things land

Every item has a logical id, like editors/vscode, and its paths under the home folder, with $XDG_CONFIG_HOME read on each machine (~/.config when it isn't set). The sender packs each item under its id; the receiver unpacks into a staging folder and moves each part to its own path for that item. Whatever was there is kept next to it as <name>.before-linysync. Each transfer gets a folder at ~/LinySync/<transfer>, with the lists in lists/.

The brief

When everything is in place, the receiver writes GOAL.md into the transfer folder: every item, where it landed, any problems, a note on what is left to do for each, and, when the home folders differ, which paths to rewrite. The package lists are in lists/: your agent installs each tool with this distro's manager and puts what has no match in TODO-FOR-YOU.md. Hand it to the agent you use, for example:

cd ~/LinySync/<transfer> && claude "Read GOAL.md in this folder and do what it says."

Done means every item works, or is in TODO-FOR-YOU.md with steps.

Security

The small things on GitHub (the offer, the picks, the stream key) are sealed boxes to the other device's public key (X25519, XSalsa20-Poly1305). Files go as an XChaCha20-Poly1305 stream under a random key only the two devices know; every frame is authenticated, so a wrong key gets nothing and a cut stream fails instead of ending early.

Command line

linysync                               open the window
linysync --scan                        what this device could send
linysync --give <id> [--only a,b]      ask device <id> to receive, then send
linysync --accept [--only a,b]         approve the request waiting here, then do this side
linysync --id                          this device's id, name and look

--only takes item ids or their starts, as --scan lists them; without it the receiver takes everything offered. A device that doesn't run Linux is refused.
